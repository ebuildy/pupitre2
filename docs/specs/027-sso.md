Covers the original 027 (configured OAuth / OIDC providers), 028 (runtime OIDC), 029 (OIDC bootstrap from the
deployment), 030 (LDAP), 031 (account provisioning and linking), 032 (group sync and role), 033 (authoritative admin
groups), 134 (group → role mappings) and the SSO part of 038.

## Providers

- **Runtime OIDC (028)**: settings `oidc_enabled`, `oidc_name` (button label), `oidc_provider_url` (discovery or issuer
  URL), `oidc_issuer_url` (expected `iss`, split-horizon), `oidc_redirect_base`, `oidc_browser_base_url` (rewrites the
  authorize host for browsers), `oidc_client_id`, `oidc_client_secret` (secret: shown as `********`, sending it back
  keeps it), `oidc_scopes`, `oidc_group_claim`, `oidc_group_admins`. Provider id `oidc`; callback
  `<redirect base>/api/sso/oidc/callback` (shown on the settings page).
- **Deployment bootstrap (029)**: with `OIDC_ENABLED=true`, the `OIDC_*` variables (`OIDC_CLIENT_SECRET_FILE` wins over
  `OIDC_CLIENT_SECRET`) overwrite the settings at every start; empty ones are skipped.
- **Deploy-time providers (027)**: `SSO_PROVIDERS_FILE`, YAML `providers: [{id, name, type: github|gitlab|google|oidc,
  clientId, clientSecret, issuerUrl, scopes?, groupClaim?}]`; secrets overridable by `SSO_<ID>_CLIENT_SECRET[_FILE]`;
  GitLab and Google are OIDC with their default issuers; GitHub uses OAuth2 and its API (primary verified e-mail).
- **LDAP (030)**: settings `ldap_enabled`, `ldap_server_url`, `ldap_bind_dn` + `ldap_bind_password` (secret, optional
  service account), `ldap_user_base_dn`, `ldap_user_filter` (`%s` = the typed username, escaped), `ldap_group_base_dn`,
  `ldap_group_filter` (`%s` = the user's DN). `POST /api/sso/ldap/login {identifier, password}`: search, bind as the
  user, display name `displayName` → `cn` → `givenName sn`, groups' `cn`; 400 `LDAP not configured`, 401 `Invalid email
  or password`, rate-limited like local sign-in.

## Flow (OAuth / OIDC)

`GET /api/sso/providers` → `{providers: [{id, name, kind}]}`. `GET /api/sso/:provider/authorize?redirect=` stores a
signed transaction (state, nonce, PKCE verifier, redirect — kept only if `safeRedirectPath()` accepts it, spec 025; 10 min) in an httpOnly cookie and redirects to the provider
(`login_hint` is passed through). `GET /api/sso/:provider/callback` checks the state, exchanges the code (PKCE), verifies
the ID token (JWKS, or HS256 with the client secret; issuer, audience, nonce), merges the UserInfo claims (they win),
then signs the user in (a better-auth session cookie) and redirects to the landing page (spec 025). Failures go to
`/login?sso_error=<access_denied|state|conflict|inactive|no_email|unknown_provider|failed>`, shown on the login page
("Accès refusé — vous avez annulé la connexion.", "La demande de connexion a expiré…", "Un compte existe déjà avec cette
adresse e-mail et une autre méthode de connexion.", "Ce compte est désactivé.", …).

## Accounts (031)

1. Known identity (provider + subject in better-auth's `account` table) → that user; avatar and bio refreshed.
2. Known e-mail → linked, unless the account signs in another way (local password included): refused (`conflict`).
3. Otherwise a new active `student` (username from the name, made unique), in the default group (038). SSO-only
   accounts have no password (no password form, local sign-in fails).
4. A deactivated account is refused.

## Groups and roles (032, 033, 134)

At each SSO / LDAP sign-in: the user's identity-provider memberships (`origin: idp`) not in the received groups are
removed (with the course access they gave); received groups are created if needed (`origin` = provider) and joined —
manual memberships are never touched. Mappings (`/api/admin/idp-mappings`, "Mappings de rôles (SSO)" on
`/admin/groups`: group name → platform role `student` / `manager` / `admin` and / or group role `member` / `manager`)
apply: a mapping to admin always wins, otherwise the last mapped role, unless the user is already admin. With
`oidc_group_admins` set (033), it is authoritative for the runtime OIDC provider: in a listed group → admin, otherwise
student.

## UI

Login page (both apps): one "Continuer avec <name>" button per provider above the form ("ou" separator); "Identifiant" /
"LDAP" tabs when LDAP is enabled ("identifiant LDAP", error "Identifiants LDAP invalides"). Admin settings: "🌐 OIDC
(OpenID Connect)" and "🗂️ LDAP / Active Directory" sections.

## SSO demo (Keycloak)

`pnpm dev:sso` (`docker/keycloak/dev-sso.sh`) starts `docker/keycloak/compose.yaml` (Keycloak 26 on
`http://localhost:8180`, console `admin` / `admin`, `KEYCLOAK_PORT` to change it) and waits for it to be healthy, then
runs `pnpm dev` with the runtime OIDC provider bootstrapped from `OIDC_*` (029) and its own database
(`apps/api/data/sso-demo.db`, `SSO_DEMO_DATABASE_URL` to change it), so the usual dev database is left alone.
`pnpm sso:down` stops Keycloak.

The realm `pupitre` (`docker/keycloak/realm-pupitre.json`, imported at start) has the confidential client `pupitre`
(secret `pupitre-demo-secret`, PKCE S256, callbacks on `localhost:3000` and `localhost:3100`) and a group-membership
mapper that puts the groups (`groups`, names without path) in every token. It has no `groups` scope, so the demo asks
for `openid email profile`. The demo accounts have the dev accounts' usernames and passwords (spec 015), and their own
`@keycloak.pupitre.local` addresses: the same e-mail as a local account would be refused (`conflict`, 031).

| Keycloak user | Password | Groups | pupitre role |
| --- | --- | --- | --- |
| `etudiant` (Élise Keycloak) | `Student@1234` | Équipe Plateforme | student |
| `manager` (Marc Keycloak) | `Manager@1234` | pupitre-managers | manager (mapping) |
| `admin` (Ada Keycloak) | `Admin@1234` | pupitre-admins | admin (mapping) |

The mappings come from the fixtures (spec 015). The opt-in e2e tests (`describe` "Keycloak SSO demo" in
`e2e/global-settings.spec.ts`) sign each account in through the real Keycloak:
`KEYCLOAK_URL=http://localhost:8180 pnpm test:e2e --project global-settings --no-deps -g Keycloak`; they are skipped
without `KEYCLOAK_URL`.

Group names and mapping names are compared with SQLite's `lower()` on both sides (`sameName`, `src/lib/sql.ts`): it
only folds ASCII, like the unique `lower(name)` index on groups, so "Équipe Plateforme" from the IdP finds the existing
group.

## Differences from the original

- One SSO endpoint set under `/api/sso` (better-auth owns `/api/auth`); PKCE and nonce added; the state lives in a cookie.
- Every provider (deploy-time ones included) gets the active check and the group sync (the original's 027 gap); manager
  mappings work (032 gap).
- No `oidc_insecure_skip_verify`.
